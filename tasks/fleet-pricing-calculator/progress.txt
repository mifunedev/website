### US-001 — fleet arithmetic in src/config/cloud-pricing.ts — DONE (1dc1d77)
New exports: HOURS_PER_MONTH (730), monthlyHourPresets, FleetQuantities, emptyFleet,
fleetNodeCount, fleetHourlyUsd, fleetTotalUsd, formatUsdTotal, entryPlan. formatHourlyUsd is
untouched and still 4dp.

Three decisions that are load-bearing rather than stylistic:

- emptyFleet() derives from cloudNodePlans instead of the literal {small:0,medium:0,large:0}.
  This is the single rule that makes the upstream three-to-five change a data-only edit.
- Sums accumulate in integer ten-thousandths and divide once. A published rate carries four
  decimals, so it is an exact integer count of ten-thousandths. In plain float, 0.0384*5 is
  0.19199999999999998, and that error would then be multiplied by 730.
- formatUsdTotal is a SECOND formatter, not a widened formatHourlyUsd. An hourly RATE is a
  published price and rounding $0.0384 to $0.04 restates it by 4.2%. A period TOTAL is a
  dollars-and-cents figure compared against an invoice. Hand-rolled rather than Intl.NumberFormat
  so server and client emit byte-identical strings — Intl output depends on the runtime's ICU
  build, and a mismatch is a hydration error on a price.

### Defect found by the browser pass and fixed — stepper batching (8fdf319)
The stepper called setQuantity(spec, quantity + 1) with quantity read from the render closure, so
every increment landing in the same React batch computed from the same stale value and all but one
was lost. Three clicks in one tick produced 1.

Ordinary clicking was never affected — separate user clicks are separate ticks with a render
between them, which is why the first browser pass, driving one click per invocation, correctly read
3 and 2. It surfaced only when three clicks were dispatched inside a single eval.

Left alone this is a trap rather than a bug: any future caller stepping twice without an
intervening render silently loses one and nothing here would fail. adjustQuantity now moves by a
delta read INSIDE the updater. The typed-input path keeps the absolute form, which is correct
there — the value the visitor typed IS the quantity.

Re-verified against the input that had failed: three clicks in one batch give 3, two give 2.
